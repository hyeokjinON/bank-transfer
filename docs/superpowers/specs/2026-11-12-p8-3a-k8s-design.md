# P8-3a Kubernetes 로 옮기기 (kind) — 설계

> 날짜: 2026-11-12 · 브랜치 `feat/p8-3a-k8s` · 기준 main `d2416ff` (P8-2 #27 · 정리 #28 머지)
> P8 전체: P8-1 게이트웨이 분리 (완료) → P8-2 앱 이미지 · Compose (완료) → **P8-3a Kubernetes 로 옮기기 (이 문서)** → P8-3b 게이트웨이 이중화 (active-standby, 별도 설계)
> 앞 단계가 넘긴 것 (ADR-0016 "다음"): Deployment · Service · 입구, readiness 에 게이트웨이 `bankConnection`(liveness 제외), NetworkPolicy, 게이트웨이 이중화. 이중화는 리더 선출 등 새 코드가 필요해 P8-3b 로 나눈다.

## 1. 목표와 성공 기준
P8-2 는 Compose 로 api 2대를 띄워 "2대가 되면 무엇이 깨지나" 를 확인했다. P8-3a 는 같은 구성을 **Kubernetes 로 옮기고**, 실무에서 실제로 사고가 나는 지점(배포 · 외부 장애 · 망 정책 · 노드)을 **단계마다 실험으로 점검**한다.

성공 기준:
1. `bash infra/k8s/up.sh` 한 번으로 kind 클러스터 + 인프라 + 앱 + 입구가 뜨고, 스모크가 로컬과 CI 에서 통과한다.
2. **R1** 롤링 업데이트에서 preStop 10초면 5xx 0. preStop 0초와의 차이를 숫자로 남긴다 (차이가 안 나면 안 났다고 쓴다).
3. **B1** 은행 장애에서 게이트웨이 재시작 0, 접수된 출금 전부 `COMPLETED`, 이중 0. **B2** (안티패턴 대조)에서 재시작이 보인다.
4. **N0** 허용 안 된 Pod 는 막히고, **N1** 스모크는 통과한다.
5. **D1** drain 중 api 가 항상 1대 이상 ready. **D2 · D2'** 노드 장애 복구 시간을 잰다.
6. 처리량은 재지 않는다 (한 PC — P8-2 와 같은 이유).

진행은 **단계 1 → 5** 순서이고, 각 단계의 점검을 통과해야 다음 단계로 간다 (§11-3).

## 2. Compose → Kubernetes 대응
| P8-2 (Compose) | P8-3a (K8s) | 달라지는 점 |
|---|---|---|
| nginx `127.0.0.1:8000` | Gateway API `Gateway` + `HTTPRoute` (Envoy Gateway) | ingress-nginx 는 2026-03 은퇴 → Gateway API. 재시도를 설정하지 않으면 다시 보내지 않는다 (P8-2 "보낸 POST 는 다시 안 보냄" 유지) |
| nginx `upstream api-1 · api-2` | Service `api` (EndpointSlice) | 주소가 고정이라 "컨테이너를 다시 만들면 nginx 재시작" 문제가 없다 |
| 서비스 api-1 · api-2 | Deployment `api` replicas 2 | 이름은 Pod 이름 (`INFO_INSTANCE` = downward API) |
| healthcheck (readiness) | startup · readiness · liveness 3종 | 실패 시 동작이 다르다 (§6) |
| `restart: unless-stopped` (`docker kill` 은 재시작 안 함, E4) | Deployment 가 항상 replicas 를 맞춤 | 자동 재생성 |
| `stop_grace_period` 30s | `terminationGracePeriodSeconds` 45s + `preStop` sleep 10s | 엔드포인트 전파 지연을 preStop 이 흡수 (§6-2) |
| 포트 미공개 (내부망) | NetworkPolicy 기본 거부 + 허용 목록 | 같은 네트워크 안에서도 막는다 (§8) |
| 공통 env 블록 (`x-api-env` 등) | ConfigMap `app-config` + Secret `db-credentials` | 점검 설정이 api · 게이트웨이 한 곳 (ADR-0015 위험) |
| 볼륨 `bank-files` (대사 파일 공유) | **없음 — 범위 밖** | RWX 볼륨 필요. 실무는 SFTP · 파일 전문으로 받는다 (§13) |
| `mem_limit` | `resources.requests/limits` | OOM 은 `OOMKilled` 로 보인다 |

## 4. 클러스터와 배치
### 4-1. `infra/k8s/kind.yaml`
- 노드: control-plane 1, worker 2. 노드 이미지 · kind 버전은 계획에서 **2주 이상 지난 안정 릴리스**로 고정한다.
- `extraPortMappings`: control-plane 의 NodePort `30080` → PC `127.0.0.1:8000` (`listenAddress: 127.0.0.1` — P8-2 와 같이 LAN 에 열지 않는다).
- control-plane 에 라벨 `bank-transfer/role=infra`. 인프라 Pod 는 이 라벨의 nodeSelector + control-plane taint 에 대한 toleration 을 가진다.
- 워커 두 개에 라벨 `bank-transfer/role=app`. 앱 Pod 는 nodeSelector 로 워커에만.

### 4-2. 분산 배치
- api: `topologySpreadConstraints` (`topologyKey: kubernetes.io/hostname`, `maxSkew: 1`, **`whenUnsatisfiable: ScheduleAnyway`**). `DoNotSchedule` 이면 워커 하나가 죽었을 때 남은 노드에 두 번째 api 를 못 띄운다 — 이중화가 복구를 막는 함정.
- 확인: `kubectl get pods -o wide` 로 api 두 개가 다른 워커에 있는지 (스모크가 확인).

### 4-3. 저장소
- kind 기본 `local-path` StorageClass. PV 는 **한 노드에 묶인다**(nodeAffinity) → StatefulSet Pod 는 다른 노드로 못 간다. 실제 장애 없이 `kubectl get pv -o yaml` 의 nodeAffinity 로 확인해 문서에 남긴다.

- Flyway 는 api 두 Pod 가 동시에 떠도 DB 잠금으로 한 번만 적용된다 (Flyway 기본 동작 — 스모크에서 두 Pod 모두 ready 로 확인).

## 6. 프로브 · 종료 · 롤링 업데이트 (단계 2)
### 6-1. 프로브
| 프로브 | 경로 | 주기 · 한도 | 실패하면 |
|---|---|---|---|
| startup | `/actuator/health/liveness` | 5s · 24회 (120s) | 기동 중 liveness 가 죽이지 못하게 |
| readiness | `/actuator/health/readiness` | 5s · 2회 | Service 에서 빠짐 (재시작 없음) |
| liveness | `/actuator/health/liveness` | 10s · 3회 | 재시작 |

api 의 readiness 그룹은 Spring 기본(`readinessState`)이다 (결정 9). 게이트웨이는 §7.

### 6-2. 종료 순서
```
Pod 삭제 ─┬─ (A) EndpointSlice 에서 빠짐 → Envoy · kube-proxy 에 전파 (비동기, 수 초)
          └─ (B) preStop sleep 10s ← A 가 끝날 때까지 새 요청도 받아 준다
                 → SIGTERM → Spring graceful (readiness REFUSING, 처리 중 요청 마무리, Kafka 그룹 정상 탈퇴, 단계당 20s)
          terminationGracePeriodSeconds 45s 를 넘으면 SIGKILL
```
- preStop 은 **K8s 내장 `sleep` 동작**(`lifecycle.preStop.sleep.seconds`)을 쓴다 — 이미지의 셸에 기대지 않는다. 노드 이미지의 K8s 버전에서 이 기능이 켜져 있는지 계획에서 확인한다 (없으면 `exec: sleep`).
- 앱 설정(graceful 20s)은 바꾸지 않는다. 45s 는 10 + 20 + 여유.
- 롤링 업데이트: `maxUnavailable: 0`, `maxSurge: 1`.

### 6-3. 실험
| 실험 | 방법 | 볼 것 |
|---|---|---|
| R1 롤링 업데이트 | 부하 중 이미지 태그를 바꿔 배포. **preStop 0s vs 10s** (experiment overlay) 각 2회 | 5xx · 연결 실패 수, 정확성 (이중 0 · 누락 0) |
| R2 Pod 강제 삭제 | 부하 중 `kubectl delete pod --grace-period=0 --force` (api 하나), 3회 | 대체 Pod 생성 → ready 시간, Kafka 파티션 넘김 (P8-2 E4 의 45s 와 비교), 이중 0 |
| R3 태그 함정 | 같은 태그로 `kubectl apply` | 롤링이 일어나지 않음 → `dev-<sha>` 규칙의 근거 |

## 7. 은행 장애 readiness (단계 3)
- 게이트웨이 설정: `management.endpoint.health.group.readiness.include: readinessState,bankConnection`, liveness 그룹은 기본(`livenessState`). 이 설정을 고정하는 테스트를 먼저 쓴다 (TDD).
- 은행이 죽으면: 게이트웨이 not ready → Service `bank-gateway` 대상 0 → api 의 연결 시도 실패 → P8-1 분류 "안 보냄" → 재시도 토픽 → 은행 복구 → ready → `COMPLETED`. 대상 0 인 Service 로의 연결이 **즉시 거부**되는지(kube-proxy)는 추정 — B1 에서 확인한다. 거부가 아니라 시간 초과면 그것도 연결 단계 실패라 "안 보냄" 이다 (P8-1 분류표).

| 실험 | 방법 | 볼 것 |
|---|---|---|
| B1 | 부하 중 mock-bank 를 replicas 0 → 60s 뒤 1 | 게이트웨이 `restartCount` 0, readiness 전환 시각, 출금 전부 `COMPLETED` · 이중 0, 그동안 1원인증 응답 코드 |
| B2 (대조) | experiment overlay 에서 `bankConnection` 을 **liveness 에도** 넣고 같은 장애 | 재시작 횟수 · `CrashLoopBackOff` · 은행 복구 뒤 ready 까지 시간 (B1 과 비교) |

## 8. NetworkPolicy (단계 4)
| 받는 쪽 | 허용하는 보낸 쪽 |
|---|---|
| (namespace 전체) | 기본 거부 (`podSelector: {}`, `policyTypes: [Ingress]`) |
| api :8080 | Envoy Gateway 프록시 (namespace `envoy-gateway-system`) |
| bank-gateway :8082 | api |
| mock-bank :9090 | bank-gateway |
| mysql :3306 · redis :6379 | api |
| kafka :9092 · :9093 | api, kafka |

- 프로브(kubelet → Pod)가 막히지 않는지 확인한다 (보통 노드 발 트래픽은 허용 — 추정).

| 실험 | 방법 |
|---|---|
| N0 집행 확인 | 정책 전: 임시 Pod(`curlimages/curl`, 버전 고정)에서 `bank-gateway:8082` · `mysql:3306` 접속 성공 → 정책 적용 → 실패. **막히지 않으면** kindnet 을 Calico 로 바꾸고 기록한다 |
| N1 정상 경로 | 정책 적용 상태에서 스모크 전체 통과 |

## 9. PDB · 노드 (단계 5)
- PDB: api `minAvailable: 1`. 게이트웨이 · 모의 은행 · 인프라(1대)는 PDB 없음 — 1대에 `minAvailable: 1` 을 걸면 drain 이 끝나지 않는다.

| 실험 | 방법 | 볼 것 |
|---|---|---|
| D1 drain | 부하 중 워커 하나 `kubectl drain --ignore-daemonsets --delete-emptydir-data` → `uncordon` | api ready 수 최소값 (≥ 1), 5xx, 게이트웨이 · 모의 은행이 그 노드에 있었으면 그 중단 시간 |
| D2 노드 장애 | 부하 중 워커 노드 컨테이너 `docker stop` → 일정 시간 뒤 `docker start` | NotReady 감지 시각, Pod Ready=False · 엔드포인트 제외 시각, 그 사이 5xx, 대체 Pod 생성 시각 (기본 약 5분 예상 — 추정), Kafka 넘김, 정확성 |
| D2' 손잡이 | 같은 장애, api 에 `tolerations` `node.kubernetes.io/unreachable` · `not-ready` `tolerationSeconds: 30` | 복구 시간 차이와 대가 (짧은 네트워크 끊김에도 Pod 를 옮김) |

## 11. 검증
### 11-1. 자동 테스트
- 게이트웨이: readiness 그룹에 `bankConnection` 포함, liveness 그룹에는 없음 (`/actuator/health/readiness` · `liveness` 응답으로, 은행 미연결 상태에서 readiness DOWN · liveness UP).
- 매니페스트: CI 에서 `kubectl kustomize` 로 모든 overlay 가 빌드되는지.

### 11-2. CI `k8s-smoke` 잡 (20분 제한)
kind 생성(설정 파일 같음) → 이미지 3개 빌드(gha 캐시, P8-2 와 같은 방식) → `kind load` → `up.sh` 의 설치 단계 → `overlays/ci` 적용 → `smoke.sh` (N0 포함) → 실패 시 `kubectl get/describe/logs` 출력.

### 11-3. 단계별 점검 (로컬)
| 단계 | 끝나는 조건 |
|---|---|
| 1 이식 | `up.sh` → `smoke.sh` 통과, Postman `127.0.0.1:8000` 확인 |
| 2 프로브 · 종료 | R1 · R2 · R3 |
| 3 은행 장애 | B1 · B2 |
| 4 NetworkPolicy | N0 · N1 |
| 5 노드 | D1 · D2 · D2' |

실패하면 원인을 측정 문서 "측정 중 생긴 일" 에 남기고 고친 뒤 다음 단계로 간다.

### 11-4. Postman 직접 확인 (머지 전, 사용자)
PR 본문에 표로: 모드 확인(Compose `app` 프로필 내림, `up.sh`, `kubectl get pods -o wide`, `/actuator/info` 두 번 → Pod 이름 두 개), 1원인증 · 출금 · 멱등 · `kubectl delete pod` 뒤에도 출금 성공 · 내부 포트 접속 불가.

## 13. 위험
- **PC 메모리**: 클러스터 + 인프라 + 앱 + Envoy 약 5 ~ 6GB 예상 (추정). Docker Desktop 메모리 한도를 먼저 확인하고 SETUP 에 적는다.
- **버전 고정**: Gateway API · Envoy Gateway · kind 노드 버전이 맞지 않으면 설치가 실패한다. 계획에서 호환 표를 확인하고 고정한다.
- **kindnet NetworkPolicy 집행**: 최신 문서상 지원하지만 어느 버전부터인지 확인 못 함 → N0 가 먼저 확인, 실패 시 Calico.
- **D2 의 노드 재시작**: `docker start` 뒤 노드가 돌아오지 않으면 클러스터를 다시 만든다 (`down.sh` → `up.sh`). 실험 데이터는 그 클러스터의 것이라 잃어도 된다.
- **Compose 와 포트 충돌**: 둘 다 `127.0.0.1:8000`. `up.sh` 가 시작 전에 포트를 확인하고 안내한다.
- 게이트웨이 1대는 여전히 단일 장애점 (P8-3b).
