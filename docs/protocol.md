# 모의 은행 전문 규격 v0.3

이 프로젝트에서 새로 정의한 학습용 규격입니다. 실제 은행 규격이 아닙니다.
국내 펌뱅킹 전문의 일반적인 모양(길이부 + 공통부 + 개별부, 고정길이, EUC-KR)을 따랐습니다.

## 1. 프레임

```
+--------+------------------------------------------+
| 길이부  |                 본문                      |
| 4 byte | 공통부 33 byte + 개별부 (업무별 고정길이)   |
+--------+------------------------------------------+
```

- 길이부: 본문 길이를 **ASCII 숫자 4자리**로 표현 (`"0052"`). 바이너리 int 가 아니다.
- 최대 본문 길이: 9999 바이트
- 길이부가 숫자가 아니면 수신 측은 **연결을 끊는다**. 경계를 잃은 스트림은 복구할 수 없기 때문이다.

## 2. 필드 규칙

| 타입 | 정렬 | 채움 | 예 (길이 8) |
|---|---|---|---|
| 문자 (AN) | 왼쪽 | 공백 `0x20` | `홍길동  ` (6바이트 + 공백 2) |
| 숫자 (N) | 오른쪽 | `0` | `00000042` |

- 길이 단위는 **바이트**. 문자셋은 EUC-KR 이라 한글 1자 = 2바이트.
- 문자 필드가 넘치면 **글자 단위로 자른다**. 한글 2바이트 중 1바이트만 남는 깨진 글자를 만들지 않는다.

## 3. 공통부 (33 byte)

| 순서 | 필드 | 타입 | 길이 | 값 |
|---|---|---|---|---|
| 1 | 전문구분 | AN | 4 | `0200` 업무요청, `0210` 업무응답, `0800` 관리요청, `0810` 관리응답 |
| 2 | 업무구분 | AN | 3 | `PLL` 폴링, `NAM` 성명조회, `TRF` 이체, `INQ` 결과조회 (v0.2) |
| 3 | 전문번호 | N | 8 | 송신 측이 매기는 일련번호. **응답은 요청의 전문번호를 그대로 돌려준다** |
| 4 | 전문일시 | AN | 14 | `yyyyMMddHHmmss` |
| 5 | 응답코드 | AN | 4 | `0000` 정상, `1001` 계좌없음, `9999` 시스템오류 (요청은 `0000`). `2001`(원거래 없음, v0.2)은 여기에 쓰지 않는다 — 결과조회 응답 개별부의 처리결과에만 나온다 (§4) |

## 4. 개별부

| 업무 | 방향 | 필드 (길이) | 합계 |
|---|---|---|---|
| 폴링 `PLL` | 요청·응답 | 없음 | 0 |
| 성명조회 `NAM` | 요청 | 은행코드 AN(3) · 계좌번호 AN(16) | 19 |
| 성명조회 `NAM` | 응답 | 요청 + 예금주명 AN(20) | 39 |
| 이체 `TRF` | 요청·응답 | 은행코드 AN(3) · 계좌번호 AN(16) · 금액 N(13) · 적요 AN(20) · 이용기관 거래번호 AN(20) (v0.2) | 72 |
| 결과조회 `INQ` (v0.2) | 요청 | 이용기관 거래번호 AN(20) | 20 |
| 결과조회 `INQ` (v0.2) | 응답 | 이용기관 거래번호 AN(20) · 처리결과 AN(4) | 24 |

**이용기관 거래번호** (v0.2): 이체 하나를 가리키는 업무 키다. 전문번호는 세션 안에서 요청 · 응답을 짝짓는 용도라 재사용되므로 업무 키가 아니다. 출금이체는 접수 때 만든 번호(`T` + KST `yyMMdd` + 무작위 13자), 1원인증은 `V` 로 시작하는 같은 형식이다.

**결과조회 응답의 두 코드**: 공통부 응답코드는 *조회 전문 자체*가 성공했는지(`0000` 이면 조회가 처리됨), 개별부 처리결과는 *원거래*의 결과다 (`0000` 처리됨 · `2001` 원거래 없음).

## 5. 예시: 성명조회 요청 (본문 52바이트, 전체 56바이트)

```
0052 0200 NAM 00000001 20261001090000 0000 090 1002123456789___
^^^^ ^^^^ ^^^ ^^^^^^^^ ^^^^^^^^^^^^^^ ^^^^ ^^^ ^^^^^^^^^^^^^^^^
길이  구분 업무 전문번호    전문일시      응답  은행  계좌번호(16, 공백 채움)
```

결과조회 요청 (본문 53바이트 = 공통부 33 + 거래번호 20, 전체 57바이트):

```
0053 0200 INQ 00000002 20261021090000 0000 T261021ABCDEFGHIJKLM
                                           ^^^^^^^^^^^^^^^^^^^^
                                           이용기관 거래번호(20)
```

## 6. 세션 규칙

- 송신 측은 쓰기가 **30초** 없으면 폴링 요청(`0800 PLL`)을 보낸다. 수신 측은 `0810 PLL` 로 응답한다.
- **90초**(폴링 3회분) 동안 아무것도 받지 못하면 회선이 죽은 것으로 보고 연결을 끊는다.
- 끊기면 1초, 2초, 4초 … 최대 30초 간격으로 재접속한다.
- 응답 대기 시간은 3초. 넘으면 요청 측은 실패로 처리한다. 늦게 온 응답은 로그만 남기고, 결과는 결과조회 전문으로 확정한다 (P3-3a).

## 7. 대사 파일 (v0.3)

은행이 하루에 한 번 만드는 파일이다. 그날 **실제로 처리(입금)한 이체만** 담는다 — 계좌가 없어 거절한 건은 돈이 움직이지 않았으므로 없다. 1원인증 송금(`V…`)도 들어간다.
필드 규칙은 전문(§2)과 같다: AN 왼쪽 정렬 · 공백, N 오른쪽 정렬 · 0, EUC-KR, 길이는 바이트. 한 줄 = 한 레코드 + `\n`. 레코드는 모두 **59바이트**(가장 긴 상세 기준)로 공백을 채운다. 마지막 레코드 뒤에도 줄바꿈이 있다 — 없으면 쓰다 만 파일로 보고 거부한다.

| 레코드 | 필드 (길이) | 합계 |
|---|---|---|
| 헤더 `H` | 구분 `H`(1) · 처리일 `yyyyMMdd`(8) · 은행코드(3) | 12 → 59 |
| 상세 `D` | 구분 `D`(1) · 이용기관 거래번호 AN(20) · 은행코드 AN(3) · 계좌번호 AN(16) · 금액 N(13) · 처리시각 `HHmmss`(6) | 59 |
| 트레일러 `T` | 구분 `T`(1) · 상세 건수 N(9) · 금액 합계 N(18) | 28 → 59 |

- 파일 이름 `RECON_yyyyMMdd.dat`, 위치 `{bank-files}/recon/`. 날짜 = 처리 시각의 KST 날짜. 처리한 이체가 없는 날도 헤더 + 0건 트레일러 파일을 만든다.
- 받는 쪽 검증: 모든 줄 59바이트, 첫 줄 `H` · 마지막 줄 `T`, 헤더 날짜 = 대사일, 트레일러 건수 · 합계 = 상세, 날짜 · 시각은 실제로 있는 값(엄격 해석 — `20260230` · `240000` 은 거부). 하나라도 틀리면 그 파일을 믿지 않는다 (`FILE_INVALID`).
- 받는 쪽은 `V…` 이면서 금액 1원인 줄만 1원인증으로 보고 대조하지 않는다. `V…` 여도 1원이 아니면 다른 줄처럼 대조한다 (우리에게 없는 거래번호 → `UNKNOWN_REFERENCE`, [ADR-0010](adr/0010-daily-reconciliation.md)).
- 모의 은행은 처리할 때마다 상세 레코드를 일자별 거래 기록(`{bank-files}/journal/yyyyMMdd.log`)에 덧붙이고, 매일 00:05 (KST) 에 전날 기록으로 이 파일을 만든다 (임시 파일 → 원자적 이름 바꾸기, 이미 있으면 덮어쓰지 않음).

예 (2026-10-28, 처리 1건, 공백은 `_`):
```
H20261028090_______________________________________________
DT261028ABCDEFGHIJKLM0901002123456789___0000000030000101530
T000000001000000000000030000_______________________________
```
