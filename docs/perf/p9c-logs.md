## L3 · L4 · L5 — 잃는 줄
| 회차 | 동작 | 센 Pod | 파일에 쓴 줄 | Loki 에 들어온 줄 | `lost_lines` | `dup_lines` | 판정 |
|---|---|---|---|---|---|---|---|
| `podkill-1` | api Pod 강제 종료 | `api-68758688f-chcws` | 940 | 940 | **0** | 0 | 통과 |
| `alloykill-1` | Alloy Pod 재시작 | `api-67cfcd5478-6vc8x` | 506 | 506 | **0** | 0 | 통과 |
| `lokizero-1` | **Loki 0대 60초** | api (둘 합) | 813 | 270 (측정 당시) → **830** (재계수) | 543 → **0** | 0 | 통과 |

- **L3 · L5**: 940/940 · 506/506 — 중복도 없다. L3 는 Pod 를 지우면 kubelet 이 로그 파일도 지우므로 부하 시작 때 노드 컨테이너에서 `tail -f` 로 미리 떠 둔다 (계획에서 정한 것 19). 단 `dup_lines` 는 Loki 가 시각 · 내용이 같은 줄을 버려서 구조상 0 에 가깝고, `lost_lines` · `dup_lines` 는 순차(net) 값이다 (한계).
- **L4 는 숫자가 둘이다 — 측정 도구의 함정**:
  - 회차 중 기록: Loki 를 끈 60초(03:33:07 ~ 03:34:08 UTC) 동안 api 가 쓴 줄 **813**, 도구가 기다리는 동안 Loki 에 들어온 줄 **270** → `lost_lines` **543** 로 찍혔다. 즉 "도구가 기다림을 멈춘 때 543줄이 아직 도착하지 않았다".
  - 약 19분 뒤 같은 구간을 다시 세니 Loki 에 api 줄 **830** (≥ 813). **줄은 사라지지 않았다** — Alloy 가 보내기 실패를 지수 백오프로 다시 시도해 나중에 다 넣었고, 도구의 기다림(settle)이 그보다 짧았다. 830 − 813 = 17 은 구간 경계(초 단위 반올림) 또는 다시 보내기 중복이다 (추정, 줄 단위 비교는 하지 않았다).
  - 그래서 기록은 **최종 잃음 0 (재계수), 도착 지연 = 도구가 멈춘 때까지 543줄 미도착**. 스펙은 L4 에 기준을 두지 않았다("잃은 수를 기록") — 원자료 `lokizero-1.p9c.json` 의 543 은 도구의 기다림 한계이지 유실이 아니다.
  - 해석 (추정): ① Loki 가 1분 죽어도 로그는 **늦게라도 다 온다** — Alloy 가 읽은 위치를 다시 보내기가 끝날 때까지 앞으로 밀지 않는 것으로 보인다. ② 늦게 도착하는 동안 Loki 로 장애를 보면 그 구간이 비어 보인다 — "로그가 없다" 를 "일이 없었다" 로 읽으면 안 된다. ③ Loki 가 emptyDir 이라 꺼지기 **전** 데이터는 사라졌다 (R4). 그래서 이 회차의 L7 · L2 숫자는 복구 뒤 기간뿐이다 (`log_lines_per_s` 비어 있음 · 가린 줄 0 — "부분 기간").
  - 돈 · 접수 p95 는 영향이 없다: 접수 p95 27.20ms (켬 평균 27.19), 완료 /s 19.67 — 수집이 죽어도 앱은 그대로 (결정 F10).

## L6 — ErrorLogSurge
### ① 정상 상태 → N 확정
정상 상태 회차(steady 1 ~ 4 · podkill · lokizero · alloykill 7회)의 5분 ERROR 최대 `err5m_max` 는 모두 **0** (DLT 포함 `err5m_max_with_dlt` 도 0). 규칙 N = max(10, 0 × 3) = **10 그대로** — `rules.yml` · `p9c.sh` 를 바꾸지 않았다. 정상 상태 kind 에서 api · 게이트웨이 ERROR 는 사실상 없다 (계획에서 본 일마감 대사 파일 없음 ERROR 는 이 시간대에 안 났다).

### ② ERROR 주입 (`errfault-1`, 360초)
MySQL 트리거(`p9c_fault_verification`)로 1원인증 저장을 5초마다 실패시켰다 → 500 응답 58건 (`probe_codes` `500=58`), api ERROR 58줄. 출금 20건/s 대비 약 1% 라 `ApiHigh5xx`(5% · 2분)는 울리지 않았다 (`api5xx_fired` false — 지표로 못 잡는 오류). 접수 p95 22.19ms · 완료 /s 19.95 로 출금 돈 흐름은 그대로, 판정 통과.

| 항목 | 값 |
|---|---|
| `err5m_max` (DLT 포함 / 뺀 값) | 58 (58) |
| `surge_cross_s` (5분 ERROR 가 10을 넘은 시각, 부하 시작부터) | 56초 |
| 계산 구간 (`expected_min_s` ~ `expected_max_s`) = 넘은 시각 + [130, 200] | **[186, 256]초** (평가 1분 · `for` 2분 · `group_wait` 10초) |
| 받는 곳 도착 `surge_fired_s` | **273.9초** (UTC 03:43:03.6) |
| 규칙이 firing 이 된 시각 (`startsAt`) | UTC 03:42:03 → 도착까지 **60초** |
| `api5xx_fired` | false |
| 받는 곳의 ErrorLogSurge 알림 | 1건 (`source=logs`, `severity=warning`, `app=api`) |

- **계산 구간보다 18초 늦었다 — 기준 6 은 "부분"**. 계산은 `group_wait` 10초를 가정했는데 firing 에서 받는 곳까지 60초(50초 더) 걸렸다. 원인 후보 (추정, 확인하지 않았다): ① Alertmanager 에 같은 `alertname` 묶음이 이미 있어 `group_wait`(10초) 대신 `group_interval`(1분)을 기다림 (앞선 Task 8 시운전의 errfault 묶음), ② Loki ruler 가 firing 첫 평가가 아니라 다음 평가(1분 뒤)에 보냄. 어느 쪽이든 "평가 한 주기" 만큼이라 계산 상한에 1분을 더하면 316초 안이다 — 그래도 **계산을 맞히지 못한 것은 맞고 통과로 올리지 않는다**.
- **운영 의미**: 로그 알림은 넘은 뒤 **약 3 ~ 4.5분** 걸린다 (지표 알림 50초보다 느리다 — 5분 창 · `for` 2분 · 1분 평가). 급한 신호는 지표로, 로그 알림은 "놓치지 않기" 용이다 (F9).

### ③ 은행 2분 끊김 (`bank-1`, 끊김 120초 · 부하 180초)
| 항목 | 값 |
|---|---|
| `inhibit_ok` | **true** — `BankDisconnected` 가 울리는 동안 넣은 시험 `ErrorLogSurge` 가 Alertmanager 에서 억제됨 (`state: suppressed`, `inhibitedBy` 있음) |
| `surge_sink_firing` | 0 (은행 끊김으로 새로 울린 ErrorLogSurge 없음) |
| 받는 곳 기록 | `BankDisconnected` firing UTC 03:46:11 → resolved 03:48:11, `ErrorLogSurge` 는 03:50:03 **resolved 1건뿐** (앞 회차 errfault 의 알림이 풀린 것 — `startsAt` 03:42:03) |
| `err5m_max` / `err5m_max_with_dlt` | 40 / **773** |
| 완료 /s · 접수 p95 | 8.41 (은행이 끊긴 구간 포함) · 28.90 ms |
| 가린 줄 계좌 · 코드 · 금액 / 금지 패턴 | 11468 · 2 · 3434 / 0 |

- `err5m_max` 40 은 **앞 회차(errfault)의 ERROR 꼬리**다: 03:45:00 에 40 → 30초마다 줄어 03:48:00 에 6, 은행을 끈 03:45:25 이후 새 비-DLT ERROR 는 없었다 (측정).
- **DLT 를 포함하면 5분에 773줄** (03:48 ~ 03:52) — Spring Kafka `DeadLetterPublishingRecovererFactory` 줄. 규칙에서 이 줄을 빼지 않았다면 은행이 돌아온 뒤(`BankDisconnected` 해제 03:48:11 이후)에도 5분 창에 남아 `ErrorLogSurge` 가 억제 밖에서 울렸을 것이다 — 계획 단계의 결정(스펙 §14-2, P9b 원자료 근거)이 이번 실측으로 맞음이 확인됐다. 그래서 "은행 끊김 중 실제 ErrorLogSurge 는 울리지 않는다" 이고, 억제 규칙 자체는 **시험 알림**으로 확인했다 (`inhibit_ok`).
- 1원인증 코드 가린 줄 2 = 스모크 · 실험 도구의 1원인증, 금지 패턴 0.

## L7 — 가리기
- 모든 회차 `forbidden_lines` **0** (성공 기준 3). 0 이 "가릴 것이 없어서" 가 아니라 가린 줄이 실제로 있었다는 것으로 읽는다 — 가린 줄 수(계좌 · 금액)가 회차마다 양수다 (`steady-1` 1115 · 0 · 1080, `errfault-1` 7138 · **58** · 7081, `bank-1` 11468 · 2 · 3434).
- 코드(`BT****`)는 1원인증이 있는 회차에만 나온다: errfault 58줄 = 주입 58건, bank 2줄 = 스모크 · 도구 1원인증, steady · podkill · alloykill 0.

## 해석 · 예상과 다른 점
- **JSON 로그는 이 부하에서 비용이 잡음 수준** (측정, +1.2%) — 줄은 요청 스레드가 표준 출력에만 쓰고, 수집은 별도 Pod(Alloy)가 한다. 바이트는 거의 두 배가 되므로 보관 · 저장 용량 계획은 JSON 기준으로 잡아야 한다.
- **수집 지연은 p95 약 2.5초** — 로그 → trace 이동 중 로그 쪽 대기는 사실상 없다. 예상보다 짧다 (Tempo 쪽 8 ~ 20초가 병목, 추정).
- **L4 의 543 은 유실이 아니다** — 도구가 기다린 시간이 Alloy 의 재시도 백오프보다 짧았다. 이 발견이 "로그가 늦게 도착할 수 있다" 를 운영 문서(OPERATION §19-4)에 넣게 했다. 사실 줄은 다 왔다(재계수 830 ≥ 813)는 것은 Alloy 가 읽은 위치를 보내기 성공 뒤에야 앞으로 민다는 가설 (추정, 코드로 확인하지 않았다).
- **ErrorLogSurge 도착이 계산보다 18초 늦었다** (L6 ②) — 계산식에 "평가 한 주기" 가 빠져 있었다. 알림 지연은 지표 알림(약 50초)보다 훨씬 길고(3 ~ 4.5분), 그것이 F9 가 로그 알림을 "지표로 못 잡는 것" 에만 쓰자고 한 이유와 맞는다. 원인 후보 두 가지 중 어느 것인지는 가리지 않았다.
- **DLT 제외는 실측으로 정당화됐다** — `bank-1` 에서 DLT 를 포함한 5분 ERROR 가 773줄이었고, 그 줄은 은행 복구 뒤에도 남는다 (L6 ③). 규칙에 DLT 를 뺀 것이 억제 밖에서 울리는 경보를 막았다.
- **N = 10 은 "측정으로 확정" 이라기보다 "측정이 올릴 이유를 못 줬다"** — 정상 상태 최대가 0 이어서 max(10, 0 × 3) 이 시작값 10 이다. 일마감 대사 파일 없음 ERROR(대사 회차마다 Pod 당 1줄)가 N 을 정할 만큼 모이는 상황은 이번 실험 시간대(01 ~ 06시 밖)에서 시험하지 않았다.
- **정상 출금에서도 3개 서비스가 줄을 낸다** — 게이트웨이 `bank call` 한 줄(스펙 §14-5)이 있어서 trace 안에 게이트웨이 줄이 있고, 이것이 기준 2 를 가능하게 했다.

## 한계
- kind 한 호스트 — 비용은 상대 비교만, 망 지연 없음. 각 조건 1 ~ 2회 (L2 만 켬 · 끔 각 2회).
- Loki emptyDir · 보관 2일 — Loki Pod 가 바뀌면 이전 로그가 사라진다 (L4). `lokizero-1` 의 L7 · L2 숫자는 복구 뒤 기간만 (부분 기간).
- `lokizero-1` 의 기록값(543)은 도구 기다림 한계 — 재계수(830)로 보정했고 줄 단위 비교는 하지 않았다.
- 텍스트 여러 줄 스택(Kafka · 모의 은행)은 줄마다 따로 수집된다 (JSON 쪽 api · 게이트웨이는 한 줄).
- 알림 본문의 `amount=` 는 가리지 않는다 (Alertmanager → alert-sink 경로이지 로그 경로가 아니다).
- L1 해상도 약 1초 (`kubectl exec` 왕복 · 0.5초 간격).
- Redis 차감 전략 로그는 kind 기본(conditional)에서 남지 않아 실험에서 보지 못했다.
- `dup_lines` 는 Loki 가 시각 · 내용이 같은 줄을 버려서 구조상 0 에 가깝고, `lost_lines` · `dup_lines` 는 순차(net) 값이다.
- `podkill-1.rebalance.txt` 는 도구가 남기는 Kafka 컨슈머 리밸런스 줄(로거 `ConsumerRebalanceListenerInvoker` · `KafkaMessageListenerContainer`, 파티션 배정 · Pod 이름만)이다 — 계좌 · 금액 · 코드는 없음을 확인했다.
- **Grafana 화면 캡처 3장(logs → trace, trace → logs, 대시보드 4행)은 찍지 않았다** — 사람 확인(Postman 직접 확인 · 가이드 캡처)으로 남긴다. 이 문서에 그림이 없는 이유다.
