## 기준 2 를 어떻게 쟀나 (격자 vs 원 표본)
- 도구의 첫 정의(`metric_bank_back_s`)는 `query_range` 5초 격자에서 "연결 1 이 두 칸 연속" 의 첫 칸이다. 격자 칸은 저장된 표본보다 0 ~ 5초 늦고, 수집 자체도 0 ~ 5초 늦으니 최대 10초까지 벌어질 수 있다 — 그래서 6.5 · 6.7 · 8.2초가 나왔다.
- 원 표본(`banktransfer_gateway_bank_connected[W]` 를 그대로 읽은 Pod 별 표본)으로 같은 규칙(같은 Pod 의 다음 표본도 1)을 적용하면 2.4 ~ 4.5초 — 수집 간격 5초 안이다. 남는 차이는 "수집 주기의 위상 + 연결 뒤 로그인 교환" (추정).
- 기준값(5초)은 바꾸지 않았다. 대신 **두 값을 다 남긴다** (`bank_gap_diff_s` · `bank_gap_diff_raw_s`). 해석: Prometheus 에 저장된 지표는 실제와 한 수집 간격 안으로 맞다. 다만 Grafana 처럼 격자로 그려 보면 복구가 최대 약 8초 늦게 보인다 (측정).
- M1a 처럼 공백이 수집 간격(5초)보다 짧으면(1.9 · 2.0초) 지표에는 아예 보이지 않는다. 그런 짧은 공백은 `for 30s` 알림도 울리지 않으니 사람이 할 일이 없다 — 의도한 모습.
- 공백 **시작**은 지표가 늦게 본다: M1b 에서 로그상 끊김은 +0.3초인데 지표의 0 은 +9초 (죽은 리더의 마지막 표본 "연결 1" 이 다음 수집 실패까지 남는다). 지표 공백 15초 vs 로그 17.2초.

### B7 — alert-sink 가 알림을 잃은 이유와 고친 방법
- 원래 alert-sink 는 `{ printf 응답; sleep 1; } | nc -l -p 8080` 반복이었다. `sleep 1` 은 **연결이 올 때가 아니라 루프가 시작될 때** 흐른다. 알림이 1초 넘게 지나서 오면 nc 는 입력이 이미 끝난 상태로 연결을 받아, 응답만 쓰고 요청 본문을 읽기 전에 끝났다. Alertmanager 는 `200` 을 받았으니 다시 보내지 않는다 → **조용한 유실** (로그에 빈 줄만).
- 증거: `bank-1.alert-sink.txt` 3건 모두 빈 줄 (BankDisconnected 울림 · 해제), `bank-4` 해제, `gwnode-1` ScrapeTargetDown 울림 · 해제, `gwzero-1` 한 건. 같은 이유로 실험 직후 스모크 [10] (시험 알림 30초 안 도착) 이 5번 실패했다 — 시험 알림의 "울림" 은 잃고 1분 뒤 "해제" 만 도착.
- 설계 단계의 위험 B7 은 "동시에 둘이 오면 하나가 거부되고 Alertmanager 가 재시도" 였다. 실제는 **거부가 아니라 성공 응답 뒤 유실**이라 재시도도 없었다 — 대역(실험용 가짜) 도구라도 "받았다고 답했는데 안 받은" 경우가 가장 나쁘다.
- 고침: busybox `httpd` + CGI 스크립트(ConfigMap). 연결마다 프로세스가 따로 떠서 본문을 `CONTENT_LENGTH` 만큼 읽고 한 번에 로그로 쓴 뒤 200. 확인 — 시험 알림 5개를 2 ~ 3초 간격으로 → 5/5 도착, 실험(`bank-2`) 직후 스모크 [10] 통과, `bank-2` 는 울림 · 해제 둘 다 받았다.
- 그래서 고치기 전 회차의 "알림 도착" 은 **Prometheus · Alertmanager 쪽 증거로 판정**했다: M3 의 GatewayNoLeader 47초 · M4 의 BankDisconnected 50초는 받은 기록이 있다. M2 는 `bank-2` 로 다시 쟀다. M5 의 "0건" 은 alert-sink 가 아니라 Prometheus 에서 울린 알림 자체가 없음(`prom_firing_alerts` = "")으로 판정했다.

## 해석 · 예상과 다른 점
- **알림 도착 시간은 계산과 거의 같다** (49 · 50 · 47초 vs 50). 수집 · 평가 주기가 맞물리는 위상에 따라 ±5초 흔들린다 (측정).
- **억제는 Alertmanager 에서만 일어난다.** M3 에서 Prometheus 는 BankDisconnected 를 울렸고(`prom_firing_alerts` 에 있다), Alertmanager 가 `suppressed` 로 표시해 alert-sink 로 보내지 않았다 (표본 3번). 그래서 Prometheus 화면(Alerts)에는 둘 다 보인다 — "원인 하나 · 알림 하나" 는 받는 쪽 기준 (측정).
- **해제(resolved) 알림은 울림보다 늦다**: bank-2 에서 은행 복구(로그 142.5초) → 해제 169초. `for` 가 없고 평가 · 묶기 간격(1분 단위)을 기다린다 (측정).
- **노드 kill 은 지표가 가장 늦게 본다**: 지표 공백 시작 +9초, ScrapeTargetDown 은 +64 · +69초 (규칙 `for 1m`). 리더 교대 자체는 Lease 만료 15초 그대로 (리더 0 구간 15.0초).

## 한계
- kind 한 호스트 — 노드 "장애" 는 컨테이너 SIGKILL, 망 지연 없음.
- 모의 은행 — 세션 하나 · 거부 응답이 실제 은행 FEP 와 다르다.
- 수집 해상도 5초 — 공백 · 도착 시간은 ±5초. 5초보다 짧은 공백은 지표에 보이지 않는다.
- alert-sink 는 대역 — 실제 받는 곳(Slack · 텔레그램)의 재시도 · 속도 제한은 재지 않았다.
- `bank-1` · `bank-4` · `gwnode-1` · `gwzero-1` 의 원 표본 열은 사후 재측정 (도구를 고친 뒤 Prometheus 에 남은 표본으로) — 같은 정의, 같은 저장소.
