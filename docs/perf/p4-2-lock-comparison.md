# P4-2 잔고 차감 락 전략 비교 — 측정 결과

> 측정: 2026-10-27 17:03 ~ 17:36 · 코드: `1c4047f` · 설계: [P4-2 설계](../superpowers/specs/2026-10-27-p4-2-lock-comparison-design.md) · 결정: [ADR-0009](../adr/0009-wallet-debit-strategies-and-lock-comparison.md) · 절차: [OPERATION §8](../../OPERATION.md#8-부하-측정-p4-2-k6)
> 숫자는 **이 PC 기준의 상대 비교**다. 앱 · MySQL · Redis · k6 가 한 PC 의 CPU 를 나눠 쓴다. 서버는 한 대라 Redis 락의 진짜 이점(인스턴스 사이 직렬화)은 재지 않았다.

## 1. 한 줄 결론
- **핫스팟 (한 명에게 50 VU)**: 초당 접수 건수는 `conditional` 106 > `pessimistic` 99 > `redis` 81 ≫ `optimistic` 45 — 측정 전 예상한 순서 그대로다. 낙관적 락은 응답은 가장 많이 돌려줬지만(198/s) 그중 **77% 가 409** 였다.
- **분산 (500명 무작위)**: 네 전략이 624 ~ 668 req/s, p50 54 ~ 60ms 로 회차 사이 편차(최대 9%) 안이다. 경합이 없으면 락 방식의 고정 비용은 이 PC 에서 구분되지 않는다.
- **언제 무엇을**: 한 행 · 한 문장으로 되는 차감은 조건부 UPDATE 가 가장 빠르고 단순하다. 비관적 락은 같은 대기에 왕복 하나 값만 더 낸다(약 6%). Redis 락은 임계 구역을 트랜잭션 전체로 넓혀 단일 인스턴스에서는 손해(약 24%)다. 낙관적 락은 핫스팟에 쓰면 안 된다.

## 5. 해석 — 비용은 어디서 생기나
핫스팟의 접수 처리량은 **한 행을 한 번에 한 요청만 쥘 수 있는 시간**으로 정해진다. 50 VU 가 쉬지 않고 두드리므로 리틀의 법칙(동시 요청 50 ≈ 처리량 × 지연)대로 p50 이 커진다 (conditional: 50 ÷ 105.7/s ≈ 473ms, 측정 p50 458ms).

- **conditional**: 행 락은 `UPDATE` 부터 커밋까지 잡힌다 — 한 건 약 9.5ms. 이 PC 의 MySQL 은 커밋마다 redo 로그와 binlog 를 둘 다 디스크에 쓰므로(`flush_log_at_trx_commit=1` · `sync_binlog=1`, Docker Desktop 볼륨) 커밋 비용이 대부분이라고 **추정**한다 (설정은 확인, 커밋 지연을 따로 재지는 않았다). 출금 행 INSERT 는 행 락 밖이라 다른 요청과 겹쳐 돈다.
- **pessimistic**: 같은 행 락 대기에 `SELECT … FOR UPDATE` 왕복 하나가 임계 구역 안에 더해진다 → 한 건 +0.6ms, 접수 −6%. 비관적 락이 "느린 방식"이 아니라, 판단 로직을 앱에서 하려고 **락을 일찍 잡는 값**을 내는 방식이라는 것이 숫자로 보인다.
- **optimistic**: 50명이 같은 `version` 을 읽고, 한 명만 `UPDATE … WHERE version = v` 에 성공한다. 진 쪽의 `UPDATE` 도 행 락을 기다렸다가 0건이 되므로 **실패한 시도도 행을 점유**하고, 다섯 번 다 지면 409 다. 그래서 응답은 빠르게 많이 돌아오지만(p50 265ms) 접수는 절반 아래로 떨어진다. 이긴 요청만 보면 지연은 짧다(성공 p50 134ms) — 운이 좋은 요청과 나쁜 요청이 갈린다.
- **redis**: 줄을 세우는 위치가 DB 앞이라, Redis 락은 **커넥션 획득 → 출금 행 INSERT → 차감 → 원장 → 아웃박스 → 커밋 → 해제(Redis 왕복)** 전체를 감싼다. conditional 에서는 겹쳐 돌던 INSERT 와 커넥션 획득까지 직렬화되고, 다음 대기자는 Redis pub/sub 알림을 받고서야 움직인다 → 한 건 +2.9ms(+31%). 단일 인스턴스에서는 DB 행 락이 이미 같은 일을 하므로 이득 없이 임계 구역만 넓어진다. DB 커넥션을 덜 잡는 효과는 커넥션 20개가 모자라지 않은 이 부하에서는 드러나지 않았다.
- **분산**: 사용자 500명에 요청이 흩어지면 같은 행을 다툴 일이 거의 없어 네 전략의 차이(왕복 1 ~ 2개, Redis 왕복)가 회차 편차에 묻힌다. 이때 처리량을 정하는 것은 락이 아니라 커밋 처리량 · CPU 다.

## 6. 언제 무엇을 쓰나
- **한 행 · 한 문장으로 표현되는 차감 (잔고 · 재고 · 카운터)**: 조건부 UPDATE. 가장 빠르고, 별도 락 · 재시도 · 외부 의존이 없다.
- **판단이 여러 단계라 앱에서 읽고 계산해야 할 때 (잔고 + 한도 + 수수료 등)**: 비관적 락. 이 측정에서 조건부 대비 비용은 약 6% — 경합이 잦아도 쓸 만하다. 대신 커넥션을 쥔 채 기다리므로 락 대기 한도(여기서는 5초)를 반드시 짧게 둔다.
- **충돌이 드문 편집성 작업 (회원 정보 · 설정 · 관리자 편집)**: 낙관적 락. **같은 행에 쓰기가 몰리는 곳에는 쓰지 않는다** — 핫스팟에서 77% 가 409 였다.
- **DB 한 행으로 막을 수 없는 일 (외부 API 호출 직렬화 · 여러 DB/서비스에 걸친 작업 · 여러 인스턴스 중 하나만)**: Redis 분산락. 같은 DB 행을 지키는 용도로는 단일 인스턴스에서 손해이고, 정확성은 여전히 DB 가 지켜야 한다 (이 저장소는 안쪽을 조건부 UPDATE 로 둔다).
- 이 저장소의 기본 전략: **`conditional` 유지** (운영 기본 변경은 범위 밖 — 판단 근거는 ADR-0009 결과 절).

## 7. 한계
- 한 PC · 서버 한 대 (상대 비교만). Redis 락의 진짜 이점은 인스턴스가 여러 대일 때다.
- MySQL 이 Docker Desktop 볼륨 위에서 커밋마다 두 번 디스크에 쓴다. 커밋이 더 싼 환경(전용 디스크 · group commit 이 잘 되는 서버)에서는 핫스팟 처리량의 절대값이 크게 달라지고, 그만큼 Redis 왕복 같은 고정 비용의 비중은 커진다.
- 전략 순서가 고정이라 시간에 따른 PC 변화는 뒤 전략에 더 실린다. drift 확인(+1%)으로 그 영향이 작음을 봤다.
- 지표마다 따로 낸 중앙값이라 한 행의 값들이 같은 회차에서 나온 것은 아니다.
- k6 와 앱 사이가 Docker Desktop 네트워크라 연결 실패(그 외)가 드물게 생긴다 — 앱 쪽 오류가 아니다.
- 커넥션 풀(20)이 모자라는 부하(예: 200 VU)에서는 Redis 가 커넥션을 늦게 잡는 효과가 드러날 수 있다 — 이번에는 재지 않았다.
