> 부하: k6 출금 20건/s 열린 모델, 실패(5xx · 연결 실패)는 같은 멱등키로 1초 뒤 최대 3번 다시. 측정 사용자 `load-p82-u001 ~ u020`.

> 지표: `bank_sessions_*` · `bank_dup_tran_no` = 모의 은행 로그, `unknown_results` = 결과조회를 한 번 이상 거친 출금(`inquiry_attempts > 0`), `gw_acquired_s` = 동작 시각 → 새 리더의 `became leader` 로그, **은행 공백** = 모의 은행 로그의 `session closed` → 다음 `session opened` (가장 정확한 "은행에 붙은 게이트웨이가 없던 시간").

## H0 ↔ H1 — 이 단계의 핵심 숫자
같은 "게이트웨이가 있는 노드 drain" 에서:

| | 이전 구성 (H0) | 이중화 (H1, 2회) |
|---|---|---|
| 은행 세션 거부 | **7** | 0 · 0 |
| 전문번호 중복 (`3001`) | **591** | 0 · 0 |
| 결과 모름 | 0 | 0 · 0 |
| 돈 정확성 | 통과 | 통과 |

- H0 의 거부 7: preStop 10초 동안 옛 게이트웨이가 세션을 쥔 채 새 게이트웨이가 붙으려다 거부 → 재접속 백오프 (P8-3a D1 의 "4 ~ 7초 동시 연결" 이 세션 하나 은행에서는 이렇게 보인다).
- H0 의 중복 591: 새 게이트웨이가 메모리 카운터를 1부터 다시 써서 그날 이미 쓴 번호와 겹쳤다. 은행이 `3001`(처리 안 함)로 돌려보내 → 게이트웨이 `503 BANK_NOT_SENT` → api 재시도로 결국 전부 처리 (돈은 정확, 대신 591번의 헛걸음).
- preStop 을 뺀 변형에서는 거부 0 · 중복 387 — **겹침의 원인은 배포 전략(`Recreate`)이 아니라 preStop 대기**였고, 번호 문제는 겹침과 무관하게 재시작만으로 생긴다.

## 실험에서 찾은 것 (예상과 다른 점)
| 무엇 | 측정 | 해석 · 조치 |
|---|---|---|
| **모의 은행 자기 readiness 프로브가 세션을 먹었다** | 첫 정상 부하에서 세션 거부 13 (5초마다 1번) | `tcpSocket` 프로브가 TCP 연결 = 두 번째 세션. 게이트웨이가 붙기 전이면 프로브가 자리를 차지할 수도 있다. → `/proc/net/tcp` 로 LISTEN 만 확인하는 exec 프로브로 교체, 거부 0 (측정) |
| **이전 구성 → 이중화 첫 전환이 롤링으로 교착** | H0 → 이중화 적용 시 롤링이 끝나지 않음 (옛 ReplicaSet 을 2로 늘림) | 옛 Pod(선출 끔)이 세션을 쥐고 놓지 않음 → 새 리더는 거부로 NotReady → `maxUnavailable 0` 이 영원히 기다림. **첫 도입은 옛 Pod 을 먼저 내린다**(scale 0 → 적용). OPERATION §16 |
| **`docker stop` 은 노드 장애가 아니다** | H4 새 리더 4.5초 (Lease 만료 15초보다 빠름), 옛 리더 로그에 Spring 종료 훅 | 노드 컨테이너에 SIGTERM → 그 안의 게이트웨이가 정상 교대. 갑작스런 손실은 `docker kill` (H4′) |
| **두 대가 한 노드에 몰렸다** | H4′ 1차: 리더 · 대기자 모두 worker2 → 새 리더 353초 | H4 의 노드 정지 동안 대체 Pod 이 살아 있는 워커로 갔고, `ScheduleAnyway` 분산은 노드가 돌아와도 다시 퍼뜨리지 않는다. **복제본 2개가 같은 장애 영역이면 이중화가 아니다.** 실험 도구에 분산 사전 확인 추가. 운영 대책(필수 anti-affinity · DoNotSchedule · descheduler · 퇴거 대기 단축)은 ADR-0018 위험 |
| **노드 SIGKILL 에도 은행은 바로 끊김을 알았다** | H4′ 옛 세션 닫힘이 kill 뒤 약 0.3초, 유휴 정리(60초) 0회 | kind 는 같은 호스트라 노드 컨테이너가 죽으면 연결이 바로 끊긴다 (실제 노드 · 네트워크 장애라면 FIN 이 없어 유휴 정리를 기다릴 수 있다 — 추정). 그래서 공백은 Lease 만료(15초)만큼 = 14.3초. 스펙 추정 "약 60초" 는 kind 에서 재현되지 않았다 |
| **H5 egress 차단이 API 서버에 안 먹었다** | 같은 정책으로 `bank-gateway:8082` 는 막힘(종료 코드 28), `kubernetes.default:443` 은 연결(0.0016초) | kindnet 은 Pod 간 egress 는 집행하지만 API 서버(노드 IP 로 변환되는) 연결은 막지 않았다. 스펙 §9 대로 **단위 테스트로 대체**: `GatewayLeaderElectionTest` — 가짜 API 서버 "거부" · "무응답(패킷 드롭)" 둘 다 갱신 기한 안에 자기 차단, 무응답 뒤 회복 시 리더 재선출 |
| `gw_leaderless_s`(표본 기반)는 노드 손실에 쓸 수 없다 | H4′ 0.0초 | 죽은 노드의 Pod 은 노드가 NotReady 로 바뀔 때까지(약 44초) API 상 Ready · 리더 라벨 그대로 → 표본은 "리더 있음" 으로 본다. 공백은 은행 로그로 잰다 |

## 구현 리뷰가 찾은 안전 결함 (측정 전에 고침)
- **응답 없는 API 서버에서 자기 차단이 늦다**: fabric8 은 갱신 기한을 반복 시작 때만 본다 → 기한 직전 갱신이 요청 타임아웃만큼 매달리면 옛 리더가 15 ~ 20초 뒤에야 끊어 새 리더(15초)와 은행 세션이 겹칠 수 있었다. → 로컬 워치독(마지막으로 성공한 갱신 시도의 시작 시각 기준, 250ms 주기)으로 **갱신 기한 + 0.25초 안에 끊는다**. 무응답 API 서버 테스트: 고치기 전 6.5초 → 고친 뒤 기한 안.
- **워치독 뒤 리더 없음 고착**: 늦게 성공한 갱신이 Lease 를 계속 쥐는 경우 → 차단 때 선출기도 끝내 반납 · 재후보.
- **전문번호 날짜 되돌림**: 시계가 늦은 예약자가 새 날짜를 옛 날짜로 덮어 번호를 다시 내는 경우 → 저장된 날짜가 더 새로우면 예약 안 함, 깨진 기록은 덮지 않음.

## 한계
- kind 한 호스트: 노드 간 시계 차가 없다 (자기 차단의 안전은 시계 차 < 약 4.75초 전제). 노드 손실 때 TCP 끊김이 바로 전달된다.
- 모의 은행 제약은 흉내다 (실무 은행의 세션 정책 · 번호 규칙은 기관마다 다름 — 추정).
- H5 는 kind 에서 재현 못 해 단위 테스트로 대체.
- 처리량 · 지연 비교는 하지 않았다 (p95 는 참고: 정상 16 ~ 25ms, 노드 장애 회차는 api 쪽 영향으로 4.8 ~ 5.6초).
