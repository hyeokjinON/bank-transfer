# ADR-0015: 은행 게이트웨이를 별도 서비스로 분리 — 동기 HTTP, 실패 분류 유지, 기본은 직결

- 상태: 채택 (2026-11-10, [#25](https://github.com/hyeokjinON/bank-transfer/pull/25))
- 관련: [설계](../superpowers/specs/2026-11-10-p8-1-gateway-split-design.md) · [계획](../superpowers/plans/2026-11-10-p8-1-gateway-split.md) · [ADR-0001](0001-modular-monolith-ports.md) (모듈러 모놀리스, 분리 예고) · [ADR-0006](0006-inquire-instead-of-resend.md) (모르면 다시 보내지 않고 조회) · [ADR-0007](0007-retry-topic-and-bounded-republish.md) (재시도 토픽) · [ADR-0012](0012-consumer-coroutines.md) (처리량은 동시 대기 수) · [측정 결과](../perf/p8-1-gateway-split.md)

## 맥락
- api 를 여러 대로 늘리면 은행 연결과 응답 매칭이 바로 깨진다. 은행 FEP 연결(폴링 · 재접속 · 전문번호로 응답을 짝짓는 대기 표)은 프로세스 안의 상태이고, 대수를 늘리는 순간 연결이 여러 개가 되거나 응답이 엉뚱한 프로세스로 간다 (설계 §1). 이 저장소에서 대수를 늘릴 때 가장 먼저 깨지는 유일한 상태다.
- ADR-0001 이 "경계를 그대로 서비스로 떼어낸다" 고 예고했고, 은행 호출은 이미 `BankPort` 계열 포트 뒤에 있다.
- P8-2(컨테이너 · Compose) · P8-3(Kubernetes, 이중화)로 가려면 은행 연결을 한 곳이 소유해야 한다. P8-1 은 그 첫 단계로, **성능을 얻으려는 분리가 아니라 확장 · 연결 소유를 위한 분리**다.

## 결정
1. **첫 분리 대상은 은행 게이트웨이**다. 도메인별 분리(1원인증 / 출금)나 DB 분리는 범위가 크고 지금 확장을 막는 원인이 아니다.
2. **api ↔ 게이트웨이는 동기 HTTP** 다 (`apps/bank-gateway`, 포트 8082, 경로 `/internal/v1/bank/{name-inquiries,transfers,inquiries}`). 은행 호출은 결과를 알아야 다음 상태를 정하는 요청/응답이고, 출금은 이미 아웃박스 → Kafka 뒤에서 호출되어 사용자 쪽 비동기와 버퍼가 있다. 처리량은 전송 방식이 아니라 **동시에 기다릴 수 있는 수**가 정한다 (P6-1: 같은 Kafka 컨슈머가 블로킹 20.9 → 코루틴 387건/s).
3. **실패 분류는 기존 규칙 그대로**: `BankNotSentException` 만 "안 보냄", 나머지는 "모름" (다시 보내는 쪽이 더 위험하다). HTTP 클라이언트는 "은행에 확실히 안 갔다" 를 증명할 수 있을 때만 "안 보냄" 을 만든다 — 연결 실패, 연결 풀에서 연결을 못 얻음, 게이트웨이의 `503 BANK_NOT_SENT`. **503 은 `BANK_NOT_SENT` 코드가 있을 때만** "안 보냄" 이다 — 프록시 · 로드밸런서가 만든 503 은 요청이 게이트웨이에 닿았는지 모르므로 "모름" 이다. 응답 읽기 시간 초과 · 응답 전 끊김 · 502 · 504 · 본문 해석 실패는 모두 "모름" → 결과조회.
4. **HTTP 클라이언트 자동 재시도는 끈다** (WebClient `disableRetry(true)`, JDK 는 POST 를 다시 보내지 않는 기본값을 테스트로 고정). 재시도는 지금처럼 재시도 토픽 · 정리 작업만 한다.
5. **api 가 끊어도 게이트웨이는 은행 송신을 취소하지 않는다.** 보낸 전문은 되돌릴 수 없다. 늦은 응답은 버려지고 api 쪽 건은 "모름" → 결과조회로 확정된다 (`Mono.fromFuture(f, suppressCancel = true)`, MVC 판 포함 4조합에서 "클라이언트가 응답 시간 초과로 연결을 닫아도 은행에는 한 번 갔고 대기 표가 빈다" 를 테스트로 고정. 호출자 future 취소는 의존 future 라 HTTP 교환에 닿지 않는다는 것도 별도 테스트).
6. **서버 기본은 WebFlux** (DB · Kafka 없이 HTTP → 은행 TCP 를 기다리기만 하는 앱이라 이벤트 루프가 맞다), **클라이언트 기본은 WebClient** (`toFuture()` 로 기존 `CompletableFuture` 유지, 연결 풀 조절, P9 지표). 비교 판으로 MVC 비동기 서버 · JDK `HttpClient` 를 같이 구현하고 설정으로 고른다 (`spring.main.web-application-type`, `bank.gateway.http.client`).
7. **계약 DTO 는 한 모듈(`modules/bank-gateway-http`)을 서버 · 클라이언트가 같이 쓴다.** 같은 저장소 · 같은 버전 배포라 어긋날 일이 없다.
8. **게이트웨이는 1대** 다 (분리 목적이 은행 연결을 한 곳으로 모으는 것). 이중화는 P8-3.
9. **기본 모드는 `direct` 유지** (`bank.gateway.mode` = `direct | http`). 기존 테스트 · 실행 구성 · 손 확인 절차가 그대로 돌고, 분리 비용을 같은 도구로 비교할 수 있다. `http` 기본은 P8-2 에서. → **P8-2 에서 기본을 `http` 로 바꿨다** ([ADR-0016](0016-app-images-compose.md)). 테스트 공통 기반 · 측정 스크립트 · 실행 구성 `5. API (부하 측정)` · `12. API (direct 직결)` 은 `direct` 를 명시한다.
10. **망 지연 주입은 Toxiproxy** (Compose 프로필 `chaos`, Testcontainers). 같은 PC 루프백은 망 지연이 거의 0 이라 분리 비용이 작게 나오기 때문이다.

시간: 연결 1s · 연결 풀 대기 1s · HTTP 응답 5s (= 게이트웨이의 은행 응답 3s + 여유 2s — api 가 먼저 끊으면 게이트웨이는 답을 받았는데 api 는 "모름" 이 되는 건이 쓸데없이 는다).

## 결과
- **측정** (2026-11-10, 42회 + D 재측정 2회, 정확성 확인 통과 — 이중 송신 0, [측정 결과](../perf/p8-1-gateway-split.md) — 이 PC 기준 상대 비교):
  - 한 줄 결론: **분리의 목적은 성능이 아니라 확장 · 은행 연결 소유다.** 이 절의 숫자는 그 비용이 이 PC 에서 얼마였는지다.
  - A (지연 100ms): 블로킹 컨슈머 21.4 → 20.7건/s (−3.3%, 회차 흔들림 안), 코루틴 361.2 → 297.5건/s (−17.6%, 예상과 다르다 — 원인은 CPU 포화로 추정). B (지연 0): 코루틴 408.7 → 314.7건/s (−23.0%), p95 156.2 → 216.2ms.
  - B' (Toxiproxy): 프록시를 거치면 p50 이 약 +10ms 늘지만 지연 1ms → 5ms 차이는 보이지 않는다.
  - C (판 비교): 네 조합 모두 292.4 ~ 337.6건/s, 기본 대비 +10% 이상이 두 회차 모두인 판은 없다. 게이트웨이 스레드 최대 WebFlux 30 vs MVC 비동기 144.
  - D (연결 풀): 풀 32 에서 은행 최대 동시가 32 에 고정 (풀 500 은 128). 재측정 102.8 · 202.2건/s (풀 500: 293.3 · 294.6) — 두 회차 차이는 재시도 꼬리 때문이다.
  - E (웹 1원인증, 지연 500ms · 400건/s): 처리량 400.0 그대로, 시간 초과 0 · 5xx 0, p95 1030.7 → 1135.7ms (+105.0ms, 예상보다 크다).
- **판단** (설계 §8-4 기준): 다른 판이 두 회차 모두 +10% 이상이 아니므로 **기본 판(WebFlux 서버 + WebClient)을 유지**한다. 비교 판 사이에 의미 있는 차이가 없다면 스레드 수가 작고 취소 · 연결 풀 조절이 되는 쪽이 기본으로 맞다. `mode` 기본은 `direct` 유지 (측정과 무관한 결정).
- **계획이 예상 못 한 것 — 연결 풀 대기열 상한**: Reactor Netty 연결 풀의 대기열 기본 상한은 최대 연결 × 2 다. 풀 32 에서 동시 128 을 넣으면 대기열을 넘긴 요청이 `PoolAcquirePendingLimitException` 으로 즉시 거절되는데, 분류가 `PoolAcquireTimeoutException` 만 "안 보냄" 으로 알아 이를 "모름" 으로 올렸고 결과조회 경로가 측정 창 안에 끝나지 못해 처음 두 회차가 정확성 확인에 실패했다 (돈은 안전한 쪽으로 실패, 이중 0). 커밋 `7afaf5b` 에서 "안 보냄" 으로 분류하고 실제 라이브러리 예외로 단위 테스트, 풀 1 · 동시 4건 재현 테스트를 고정했다. 교훈: **실패 분류 표는 라이브러리 기본값이 만드는 예외까지 포함해야 한다.** 대기열 상한은 기본값 그대로 둔다 (빨리 거절하고 재시도 토픽이 흡수). 측정 요약 스크립트는 원자료의 종류(컨슈머 · 웹)별로 자기 파일만 읽도록 고쳤다 (커밋 `70c8ead`).
- **위험** (설계 §10):
  - 점검 시간 설정이 api 와 게이트웨이 **두 곳**이다. 어긋나면 동작이 헷갈린다 (돈은 안전 — 보류는 "안 보냄"). P8-2 · P8-3 에서 한 곳으로 모은다. 지금은 문서 · 기본값을 같게 둔다.
  - 게이트웨이 1대는 **단일 장애점**이다. 내려가면 출금은 재시도 토픽 → DLT → 재발행 한도(약 26분) 뒤 `FAILED E001`, 1원인증은 오류 응답.
  - **서비스 간 인증이 없다** (내부망 전제). 게이트웨이 포트가 외부에 열리면 누구나 이체 전문을 보낼 수 있다.
  - 측정은 한 PC · 루프백이다. 표본이 작고(2회짜리 칸 있음) CPU 포화와 HTTP 구간 비용을 가르지 못했다.
- **P8-2 · P8-3 로 넘기는 것**: P8-2 — 앱 컨테이너 이미지 · Compose 전체 실행, `mode` 기본을 `http` 로, 점검 설정 한 곳으로. P8-3 — 게이트웨이 이중화(active-standby), 서비스 간 인증 · NetworkPolicy, ConfigMap, 스케줄 중복 실행. 분산 추적 · 지표는 P9.
- 대가: 비교 판(서버 2 × 클라이언트 2)이 코드에 남아 테스트 4조합을 유지해야 한다.

## 검토한 대안
- **Kafka 명령/결과 이벤트**: 게이트웨이가 재배달을 받으면 이중 송신이 되어 게이트웨이가 멱등해야 하고, P3 처리 구조(상태 전이 · 결과 확정)를 다시 설계해야 한다. 범위가 약 2배.
- **Kafka 요청/응답**: 응답 짝짓기 · 늦은 응답 · 타임아웃을 직접 만들어야 한다 — 이미 있는 전문번호 매칭을 한 겹 더 쌓는 셈.
- **gRPC**: 도구 · 학습 비용 대비 이 규모에서 얻는 것이 적다 (경로 3개).
- **JDK `HttpClient` · MVC 를 기본으로**: 비교 판으로 구현했고, 측정에서 +10% 기준을 넘지 못해 기본은 WebFlux + WebClient 로 둔다.
- **`RestClient` + 가상 스레드**: 구현 · 측정하지 않고 말로만 비교했다 (P7 로 설명 가능 — Java 21 냉시동 교착 때문에 같은 시험이 먼저다, 결과 문서 §11).
- **OpenAPI · 계약 테스트 도구**: 팀이 갈라지면 필요하다. 지금은 DTO 모듈 공유로 충분.
- **게이트웨이 여러 대**: 연결 소유를 한 곳으로 모으는 것이 이번 목적이다 — P8-3.
