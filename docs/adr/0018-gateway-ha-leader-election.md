# ADR-0018: 게이트웨이 이중화 — active-standby, K8s Lease 리더 선출, 리더 라벨 + 둘 다 Ready, 전문번호 ConfigMap 구간 예약

- 상태: 채택 (2026-11-16, [#31](https://github.com/hyeokjinON/bank-transfer/pull/31))
- 관련: [설계](../superpowers/specs/2026-11-16-p8-3b-gateway-ha-design.md) · [계획](../superpowers/plans/2026-11-16-p8-3b-gateway-ha.md) · [측정 결과](../perf/p8-3b-gateway-ha.md) · [규격 v0.4](../protocol.md) · [ADR-0017](0017-kubernetes-kind.md) (Kubernetes — "위험 · 다음" 이 이 단계의 출발점) · [ADR-0015](0015-bank-gateway-service.md) (게이트웨이 분리 — 연결 주인 하나, 게이트웨이는 DB 를 모른다) · [ADR-0006](0006-inquire-instead-of-resend.md) (모르면 묻는다) · [ADR-0001](0001-modular-monolith-ports.md) (포트/어댑터)

## 맥락
- P8-3a D1 (3회): 게이트웨이가 있는 노드를 drain 하면 `Recreate` 인데도 새 게이트웨이가 먼저 떠서 **4 ~ 7초간 두 대가 은행에 붙었다**. `Recreate` 는 배포에만 걸리고 퇴거(eviction)에는 걸리지 않는다. 게이트웨이 1대는 단일 장애점이기도 하다 (D2: 노드 정지 때 대체까지 수 분).
- 실무 제약 (**추정** — 은행마다 다르다): 은행 FEP 는 기관당 세션 수를 제한할 수 있고, 기관 · 일자별로 전문번호 유일을 요구할 수 있다. 지금 코드의 전문번호는 게이트웨이 인스턴스마다 1부터 세는 메모리 카운터(`AtomicLong`)라, 재시작하면 같은 날 이미 쓴 번호를 다시 낸다.
- 이 두 제약을 모의 은행 옵션 3개로 재현해(`--single-session` · `--session-idle-timeout=60s` · `--unique-tran-no`, 기본 꺼짐 — K8s 에서만 켠다) **이전 구성이 깨지는 것과 새 구성이 지키는 것을 같은 부하로 비교**한다. 처리량은 재지 않는다. 돈 불변식(접수 때 차감, 같은 거래번호 은행 송신 1번, 안 보냄만 다시 보내고 모르면 묻는다)은 건드리지 않는다.

## 결정
스펙 §3 의 22개 결정 + 계획 단계에서 고친 것(스펙 §16) + 구현 중 추가한 것. 이유와 버린 대안은 스펙 표가 원본이고 여기에는 핵심만.

| # | 결정 | 이유 | 버린 대안 |
|---|---|---|---|
| 1 | **active-standby** — 은행에 붙는 것은 리더 1대 | 세션 수 제한 · 번호 유일 두 제약을 가장 단순하게 | active-active (세션 여러 개를 허용하는 은행이면 더 흔함 — 범위 밖) |

| 3 | Lease 15s · 갱신 기한 10s · 재시도 2s, 갱신 실패 시 **자기 차단** + **로컬 워치독** (아래) | 옛 리더가 늦어도 10초에 끊고 새 리더는 15초 만료 뒤 획득 | 갱신 기한 = 유효 시간, fabric8 기본 재시도 |
| 4 | **트래픽 = 리더 라벨 + Service selector, 둘 다 Ready.** 리더가 자기 Pod 에 `bank-transfer/gateway-role=leader` 를 붙이고 Service selector 가 그 라벨을 요구. 대기자 readiness = UP(`role: standby`), 리더는 은행 연결이 끊기면 DOWN (P8-3a B1 그대로), liveness 는 그대로 | 대기자가 Ready 여야 롤링(`maxUnavailable 0`) · `rollout status` · `up.sh` 준비 대기 · PDB 가 움직인다 | **readiness = 리더만 UP** (새 Pod 가 영원히 NotReady 라 롤링이 멈춘다 — 계획 단계에서 버림), `Recreate` 로 되돌리기 (배포마다 공백) |

| 6 | 예약은 **날짜가 되돌아가지 않게 안전 쪽으로**: 저장된 날짜가 더 새로우면 예약하지 않는다(시계가 늦은 예약자가 되돌릴 수 없다), 깨진 기록은 덮어쓰지 않는다. 예약 실패 · 깨진 기록이면 송신 안 함(`BankNotSentException` → `503 BANK_NOT_SENT`) — **fail-closed, 운영자가 고친다** | 번호가 겹치는 것보다 못 보내는 것이 낫다 (안 보냄은 재시도 경로, 겹침은 은행이 `3001` 로 거절) | 실패해도 송신, 깨진 기록을 새로 덮어쓰기 |
| 7 | 정상 교대 순서 (SIGTERM 종료 훅, **게이트웨이 preStop 없음**): 새 요청 거절 → 처리 중 전문 비우기(최대 5s, 거절 확인과 대기 표 등록 사이 틈은 처리 중 카운터로 닫는다 — 통과한 요청은 끊기 전에 끝난다) → 연결 끊기 → 라벨 떼기 → Lease 반납. 새 리더: 획득 → 번호 예약 → 접속 시작 · 라벨 붙이기 (라벨은 연결을 기다리지 않는다 — 그 사이 요청은 503 BANK_NOT_SENT, 안전하게 재시도) | 반납 전에 세션을 비워 새 리더가 바로 붙는다. 호출자(api)는 "안 보냄" 을 안전하게 재시도하므로 기다릴 이유가 없다 | preStop sleep 10s 유지 (공백이 길고 H0 에서 세션 거부를 일으켰다), 반납 먼저 |

| 9 | 규격 **v0.4**: 전문번호는 기관 · 일자(KST)별 유일, 응답코드 **`3001` 전문번호 중복 (처리 안 함)**. 게이트웨이는 `3001` → `503 BANK_NOT_SENT` (은행이 처리하지 않았으니 api 가 실패로 확정하면 안 된다) | 실무 제약 재현 · P8-1 실패 분류 | 응답 코드를 그대로 전달 |

**구현 중 추가한 안전 장치** (리뷰가 찾은 결함 — 측정 전에 고침, [측정 결과](../perf/p8-3b-gateway-ha.md) "구현 리뷰가 찾은 안전 결함"):
- **자기 차단 워치독** (`GatewayLeaderElection`). fabric8 은 갱신 기한을 반복 **시작 때만** 본다. 기한 직전 갱신이 요청 타임아웃만큼 매달리면 응답 없는 API 서버에서 옛 리더가 **15 ~ 20초** 뒤에야 끊어 새 리더(15초)와 은행 세션이 겹칠 수 있었다. → 로컬 워치독(마지막 갱신 시도 **시작** 시각 기준, 250ms 주기)이 **갱신 기한 + 0.25초 안에** 자기 차단한다. 차단 때 선출기도 끝내(반납 → 재후보) 늦게 성공한 갱신이 Lease 를 계속 쥐는 **리더 없음 고착**을 피한다. 무응답 API 서버 테스트: 고치기 전 6.5초 → 고친 뒤 기한 안.
- **K8s 클라이언트 빨리 실패**: 재시도 없음 · 연결 2s · 요청 5s. fabric8 기본 재시도(지수 백오프)는 API 서버 단절 때 갱신 실패를 늦게 알려 위 10초 보장을 흐린다.
- **전문번호 날짜 되돌림 방지** (결정 6).

**프로토콜 · 모의 은행**: 규격은 [protocol.md](../protocol.md) v0.4. 모의 은행의 `--single-session` 은 이미 세션이 있으면 새 연결을 받자마자 close(`session rejected`), `--session-idle-timeout` 은 전문이 없는 세션을 close, `--unique-tran-no` 는 같은 KST 날짜의 같은 번호를 `3001` 로 거절한다. 모의 은행 자기 readiness 프로브는 `tcpSocket` 이면 TCP 연결 = 두 번째 세션이 되므로 **`/proc/net/tcp` LISTEN 만 보는 exec 프로브**다.

## 결과
측정 (2026-11-16, 한 PC · kind 3노드 — 운영 수치가 아니다, [측정 결과](../perf/p8-3b-gateway-ha.md)). 판정(돈 정확성)은 **13회 전부 통과**: 접수된 키 = 출금 행 = 거래번호, 전부 `COMPLETED`, 은행 기록에 빠진 것 0 · 두 번 간 것 0, 환불 0, 잔고 = 원장 합.

- **은행에 붙는 것은 언제나 1대**: 13회 전부 동시 세션 최대 1. 이중화 구성에서 세션 거부 **0**.
- **H0 ↔ H1 (같은 "게이트웨이 노드 drain")**: 이전 구성(1대 · `Recreate` · preStop 10s · 선출 끔) 세션 거부 **7** · 번호 중복(`3001`) **591** → 이중화 2회 모두 거부 **0** · 중복 **0**. 결과 모름은 둘 다 0, 돈은 둘 다 정확 (H0 은 `503 BANK_NOT_SENT` → api 재시도로 결국 전부 처리 — 591번의 헛걸음). preStop 을 뺀 H0 변형은 거부 0 · 중복 **387** — 번호 중복은 겹침과 무관하게 **재시작만으로** 생긴다.
- **교대 공백**(모의 은행 로그의 `session closed` → 다음 `session opened`): drain · 롤링 · 강제 삭제 6회 **1.1 ~ 3.7초**, 결과 모름 **0** (스펙 추정 3 ~ 7초보다 짧다).
- **H4 · H4′ 노드 손실**: `docker stop` 은 노드 컨테이너에 SIGTERM 이라 정상 교대와 같다(공백 4.3초 — 노드 장애가 아니다). **`docker kill`(갑작스런 손실) 은 새 리더 14.6초 · 은행 공백 14.3초** = Lease 만료(15초)만큼. 돈 정확, 결과 모름 0. 스펙 추정 "약 60초"(세션 유휴 정리 대기)는 kind 에서 재현되지 않았다 — 같은 호스트라 노드 컨테이너가 죽으면 연결이 바로 끊긴다 (실제 노드 · 네트워크 장애라면 FIN 이 없어 유휴 정리를 기다릴 수 있다 — **추정**).
- **H5 API 서버 단절**: kind(kindnet)가 API 서버 egress 를 막지 않아 **재현 못 함** → `GatewayLeaderElectionTest` 단위 테스트로 대체 (가짜 API 서버 "거부" · "무응답" 모두 갱신 기한 안에 자기 차단, 무응답 뒤 회복 시 리더 재선출).
- 전체 테스트는 PR CI 기준. 스모크 [0] ~ [9] 통과.

## 위험 · 다음
- **첫 전환(이전 구성 → 이중화)은 `RollingUpdate` 로 교착한다.** 옛 Pod(선출 끔)는 선출에 참여하지 않고 은행 세션을 쥔 채 놓지 않는다 → 새 Pod 가 리더가 되어도 은행이 세션을 거부해 리더가 NotReady → `maxUnavailable 0` 이 영원히 기다린다 (H0 → 이중화 적용 때 실측). **첫 도입은 옛 게이트웨이를 먼저 내린다 (`scale --replicas=0` → 적용)** — 되돌릴 때도 같다. 절차는 OPERATION §16-5. 이후 배포(이중화 → 이중화)는 롤링이 정상이다 (H2).
- **복제본 2개가 한 노드에 있으면 이중화가 아니다.** H4′ 1차: 리더 · 대기자가 모두 worker2 에 있어 노드를 죽이니 새 리더가 **353초**(변형 `gwnode-samenode-2`). 원인은 H4 의 노드 정지 동안 대체 Pod 가 살아 있는 워커로 갔고, `ScheduleAnyway` 분산은 **노드가 돌아와도 다시 퍼뜨리지 않기** 때문이다. 운영 대책 (아직 안 함): 필수 pod anti-affinity 또는 `DoNotSchedule` 분산(단 워커 하나가 죽으면 두 번째 복제본을 못 띄운다 — 트레이드오프), descheduler 로 재분산, 노드 도달 불가 `tolerationSeconds` 단축(P8-3a D2' 88초). 확인 · 복구는 OPERATION §16-3.
- **시계 차 전제**: 자기 차단의 안전은 노드 간 시계 차 < 약 4.75초 (Lease 15s − 갱신 기한 10s − 워치독 0.25s). kind 는 같은 호스트라 시험하지 못했다. 운영은 NTP 필수.
- **API 서버 장기 장애 = 리더가 자기 차단 = 송신 중단.** 안전 쪽으로 실패하는 것이 의도다 (출금은 "안 보냄 → 재시도" 로 흐른다).
- **번호 저장소(ConfigMap)가 깨지거나 날짜가 앞서 있으면 송신이 멈춘다** (fail-closed, 결정 6). 사람이 앞으로만 고친다 — OPERATION §16-4. 지켜볼 것은 `3001` 증가와 `BANK_NOT_SENT` 로그.
- **Pod 권한이 namespace 범위** (Pod get · patch — 자기 라벨용). 게이트웨이가 탈취되면 같은 namespace 의 다른 Pod 라벨을 바꿀 수 있다. 이름 한정은 Pod 이름을 미리 몰라 안 된다.
- **전문번호 구간을 예약하면 남은 번호는 건너뛴다** (유일성만 요구한다는 추정 — 연속을 요구하는 은행이면 안 맞다).
- **한계**: kind 한 호스트(시계 차 없음 · 노드 손실 때 TCP 끊김이 바로 전달), 모의 은행 제약은 흉내(실무 은행의 세션 정책 · 번호 규칙은 기관마다 다름 — 추정), H5 는 단위 테스트로 대체, 회차당 1 ~ 2회.
- **범위 밖** (스펙 §14): active-active(세션 여러 개 은행 + 번호 공유 발급 — 이 구간 예약으로 확장 가능), Envoy outlier detection(노드 손실 뒤 약 50초 입구 5xx — H4 · H4′ 의 5xx 는 같은 노드의 api Pod 때문), 게이트웨이 재접속 백오프 상한 30초, 고정 출구 IP · 망분리 · 전용선, 대외계 VM + VIP 방식, 업무개시 · 종료 전문, 여러 은행, 서비스 간 인증(mTLS), 관측성(P9).

## 검토한 대안
- **리더만 Ready**: 롤링이 멈춘다 (대기자가 영원히 NotReady → `maxUnavailable 0` · `rollout status` · PDB · 준비 대기 · 스모크가 모두 막힌다). 리더 라벨 + 둘 다 Ready 로 바꿨다.
- **`Recreate` 유지 + preStop**: 퇴거를 못 막고(P8-3a D1), 배포마다 공백이 생긴다. H0 이 세션 거부 7 · 번호 중복 591 로 보여 줬다.
- **Lease 직접 구현**: 시간 · 경쟁 · 갱신 실패 처리를 다시 만드는 위험. fabric8 에 워치독만 덧붙이는 쪽이 작다.
- **MySQL 잠금 리더 선출**: DB 장애 = 은행 연결 장애가 되고 게이트웨이에 DB 가 들어간다 (ADR-0015 원칙 위반).
- **번호를 Lease 주석에 저장 · 시각 기반 번호**: 선출 오류가 곧 번호 중복이 된다. 구간 예약은 선출과 독립이라 두 대가 겹쳐도 번호가 안 겹친다.
- **active-active**: 은행이 세션 여러 개를 허용해야 의미가 있다. 번호 공유 발급은 구간 예약으로 확장 가능하다 (다음 과제).
